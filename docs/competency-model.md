# 全栈工程师能力模型

面向"传统后端 → 全栈"的转型标尺。跨路线通用，与具体技术栈无关；各路线的 roadmap 负责技能落地，本文负责对照检验。

## 核心判断

**全栈的价值不是"两端都会写"，而是能判断同一个问题该在哪一层解决。**

一个"列表页很慢"，可以在前端解决（虚拟滚动、分页加载）、在 API 解决（字段裁剪、游标分页）、在数据库解决（索引、物化视图）、在架构解决（缓存、CDN）。专精一端的人只会在自己那端解决，全栈的独特价值是在整条链路上选择代价最小的位置动手。

## 一、认知转变（后端出身最易低估）

技能可以按 roadmap 补齐，认知不补上，写出来的前端会是"能跑但不对味"。

- [ ] **前端是持有状态副本的客户端节点，不是展示层**
      后端思维：请求-响应、无状态、数据库是唯一真相源。前端现实：客户端手里有一份数据副本，于是有缓存失效、乐观更新、竞态请求、离线重连——本质是分布式系统问题。TanStack Query 这类库存在的理由就在此。
- [ ] **声明式取代命令式**
      从"拿到数据 → 逐步操作对象 → 输出"切换到"描述状态与 UI 的映射，框架负责变更"。继承让位于组合。需要写够代码才能内化，看文档无效。
- [ ] **性能的物理学不同**
      后端：吞吐、GC 停顿、连接池、慢查询。前端：首屏（网络往返 + 包体积 + 解析执行）、运行时（重渲染、长任务阻塞主线程导致掉帧）、内存泄漏（未清理的监听器与订阅，表现为"用久了越来越卡"）。
      **根本区别：后端能加机器，前端的"服务器"是用户那台不可控的设备，没有扩容选项。**
      工具也是另一套：不是 JFR / 堆转储，是 DevTools 的 Performance、Memory 面板与 Lighthouse。
- [ ] **对感知性能负责**
      后端只对 p99 负责。200ms 的接口没有 loading 态，用户就觉得卡；报错直接抛 JSON，功能对但体验废。
      **四态检查：加载 / 空 / 错误 / 正常——每个页面都想过，才算过关。**

## 二、硬技能

### 必须扎实（懂原理，不止会用）

- [ ] JS 语言核心与事件循环（重点：与后端线程模型的差异）
- [ ] TypeScript 类型系统（Java 底子是优势，但注意结构化类型 ≠ 名义类型）
- [ ] 一个前端框架的深度（React 即可），重点是渲染机制与状态管理边界
- [ ] 浏览器作为运行时：渲染管线、HTTP 缓存、Cookie/SameSite、CORS、同源策略
- [ ] Web 安全：XSS、CSRF、Token 存放位置——与后端是两套威胁模型

### 需要建立

- [ ] CSS 与响应式布局：不必做设计师，但 Flex/Grid 要能不查文档写出
- [ ] 端到端契约设计：分页、错误码、字段命名；OpenAPI → TS 类型打通类型链路
- [ ] 构建与交付：打包、产物分析、环境变量、CDN、前端错误监控
- [ ] 端到端延迟预算：后端省 50ms 而前端阻塞 300ms，等于白干

### 加分

- [ ] SSR/SEO 的取舍（知道何时**不需要**，比会用更值钱）
- [ ] 无障碍与语义化 HTML
- [ ] 实时通信（WebSocket/SSE）、可视化等专项

## 三、检验标准

不看会几个框架，看这几件事能否做到：

- [ ] 拿到需求，能判断哪些逻辑放前端、哪些必须在后端（校验与权限尤其：前端做体验，后端做安全，这条线不能糊）
- [ ] "页面很慢"能在网络、渲染、接口、数据库四层间定位根因，而不是靠猜
- [ ] 能设计出前端用着舒服的 API，因为自己就是消费方
- [ ] 一个功能从数据库表结构到线上可访问，全链路独立走完
- [ ] 能说清项目为何选这套栈、代价是什么——对应 [tech-radar.md](tech-radar.md) 与各路线 `evaluation.md`

## 使用方式

- 每完成一个路线阶段，回来对照勾选，缺口进入下一阶段计划
- 认知层需要刻意练习：强制处理四态、用 DevTools 而非 `console.log` 排查一次性能问题、完整打通一次类型链路
- 第 5 条检验标准是本空间的终极目标，靠多路线横向对比达成

# 前端技术全景

跨路线通用的前端技术地图。后端可以是 Java / Node / Go / Python，前端这套东西是共用的，因此放在 `docs/` 而非某条路线内。

**统一格式**：每项技术按「是什么 / 优势 / 劣势 / 适用场景 / 与谁搭配」讲，便于横向比较与选型。深入的实测结论进各路线 `evaluation.md`。

## 分层地图

前端不是一门技术，是七层堆叠。搞清每层解决什么问题，选型就有骨架：

| 层 | 解决什么 | 代表 | 本文状态 |
|---|---|---|---|
| ① 语言 | 写什么 | JavaScript / TypeScript | ✅ |
| ② 运行环境 | 在哪跑 | 浏览器 / Node.js | ✅ |
| ③ 框架 | 怎么组织 UI 与状态 | React / Vue / Angular / Svelte | ✅ |
| ④ 构建工具 | 怎么变成能上线的产物 | Vite / Webpack / esbuild | ✅ |
| ⑤ 元框架 | 怎么把前后端合起来 | Next.js / Nuxt / Remix | ✅ |
| ⑥ 配套生态 | 路由/状态/请求/UI/样式 | React Router、Zustand、TanStack Query | ✅ |
| ⑦ 工程化 | 包管理/规范/测试/部署 | pnpm、ESLint、Vitest | ✅ |

## ① 语言层

### JavaScript

**是什么**：1995 年为浏览器而生的脚本语言，标准名 ECMAScript。**浏览器唯一原生支持的编程语言**——这个垄断地位决定了前端的一切。

与 Java 的核心差异：单线程 + 事件循环（而非多线程）、动态弱类型（而非静态强类型）、原型继承（而非类继承）、函数是一等公民。

| | |
|---|---|
| **优势** | 浏览器唯一选择；npm 生态世界最大；上手快，改完刷新即见 |
| **劣势** | 动态类型使大型项目重构风险高；历史包袱重（`==` 隐式转换、`this`、`NaN !== NaN`）；单线程，CPU 密集任务卡死整个程序 |
| **场景** | Web 前端（无可选）；Node 服务端（IO 密集） |
| **搭配** | 现代项目几乎总是配 TypeScript |

### TypeScript

**是什么**：微软 2012 年推出的 **JS 超集** = JavaScript + 静态类型系统。所有合法 JS 都是合法 TS，可渐进迁移。

**最关键的一句**：**类型只存在于编译期，运行时完全不存在**（见下文「类型擦除」）。对照 Java：Java 泛型也擦除，但 `.class` 保留类信息可反射；TS 擦得更彻底，运行时一点类型信息不剩。

| | |
|---|---|
| **优势** | ① IDE 智能提示与安全重构（**最大收益，远超"找 bug"**）② 大型项目可维护 ③ 类型即文档 ④ 对 Java 开发者近乎零门槛 |
| **劣势** | ① 多一道编译步骤 ② 类型体操会失控（复杂泛型比业务代码难读）③ **运行时零保护** ④ `any` 会传染 |
| **场景** | 中大型项目、多人协作、长期维护 → 必选；几十行脚本 → 不必 |
| **搭配** | React/Vue 原生支持；**必配 zod 等做运行时校验**补上劣势③ |

**「运行时零保护」要特别当心**：声明 `const user: User = await res.json()`，TS 会信你，但接口真返回 `null` 程序照样炸。**类型系统只在自己代码内部有效，一到系统边界（网络、文件、用户输入）就失效。** 后端转前端最易误判之处。

### 类型擦除与 TS 的三种运行方式

`.ts` 不能被任何引擎直接执行，必须先变成 `.js`。方式有三：

| 方式 | 做法 | 优势 | 劣势 | 适用 |
|---|---|---|---|---|
| ① `tsc` 编译 | 官方编译器产出 `.js` | 唯一会**检查类型**；支持全部语法 | 慢；多一步；产生中间文件 | 库开发、CI 校验 |
| ② 打包器转译 | esbuild/swc 边打包边转译 | 快 10–100 倍；能处理 CSS、图片、JSX | **不检查类型**；需配置 | **浏览器项目（Vite 走这条）** |
| ③ Node 原生擦除 | Node 内置，内存里删类型 | 零配置，`node x.ts` 直接跑 | 不检查类型；**只能用可擦除语法** | 脚本、纯语言学习 |

**重要工程认知**：现代前端普遍把「类型检查」与「代码转换」**拆开**——转换用 esbuild/swc 求快，检查用 tsc 求准（编辑器实时跑 + CI 跑一次）。Vite 项目既快又类型安全，秘密在此。

方式③（Node 22.6 引入、23.6 起默认）不支持 `enum`、`namespace`、构造器参数属性——它们需要生成运行时代码，**不可擦除**。

## ② 运行环境层

### 浏览器

真正的目标环境：有 DOM、CSSOM、渲染管线、事件系统。**代码经网络下载而来，所以包体积直接等于性能**——多 1MB 就是多几百毫秒白屏。后端没有这个概念。

### Node.js

**是什么**：2009 年把 Chrome 的 V8 引擎从浏览器抠出来，让 JS 跑在服务器与命令行。

**对前端最重要的身份不是"用 JS 写后端"，而是工具链底座**——即使只写浏览器代码，构建工具、包管理器、开发服务器、测试框架全是 Node 程序。

| | |
|---|---|
| **优势** | 前后端同语言；IO 密集性能优秀；启动快、内存远低于 JVM；npm 生态 |
| **劣势** | CPU 密集弱（单线程）；异步心智负担；依赖树膨胀与供应链安全；错误处理不如 Java 严谨 |
| **场景** | 前端工具链（**必须**）；BFF 聚合层；IO 密集 API；实时服务；Serverless |
| **搭配** | 与 Java 后端**并存**而非替代——典型架构：Java 核心业务 + Node BFF + React 前端 |

### 浏览器 vs Node：同语言，不同能力

| | 浏览器 | Node |
|---|---|---|
| 有 | DOM、CSS、fetch、localStorage | 文件系统、进程、网络服务器 |
| 没有 | 文件系统（安全沙箱） | DOM |
| 代码来源 | 网络下载（**体积即性能**） | 本地磁盘（体积无所谓） |

## ③ 框架层

### 框架到底解决什么

手写 DOM 操作的痛苦。命令式要自己找元素、自己改：

```js
document.getElementById('count').innerText = count   // 状态变了要记得手动同步
```

声明式只描述映射关系，框架负责同步：

```jsx
<div>{count}</div>   // count 变了，界面自动跟上
```

**`UI = f(state)`**——所有现代框架的共同内核。前端框架的本质是「状态到视图的自动同步」，差异只在**怎么侦测状态变化**和**怎么更新 DOM**。

### React

**是什么**：Meta 2013 年开源。组件化 + 单向数据流，用 JSX 在 JS 里写 HTML。2019 年后主流写法是 Hooks（函数组件）。

| | |
|---|---|
| **优势** | 生态最大（库、方案、招聘）；心智模型简单（组件就是函数）；React Native 可复用经验；社区最活跃 |
| **劣势** | ① **过于灵活 = 什么都要自己选型**（路由、状态、请求各选一个库）② 性能要手动优化（`memo`/`useCallback`），默认容易无谓重渲染 ③ Hooks 有陷阱（闭包捕获、依赖数组）④ 升级激进（Server Components 造成生态分裂） |
| **场景** | 中大型应用、需要生态支撑、招聘友好 |
| **搭配** | Vite + React Router + TanStack Query + Zustand + Ant Design |

### Vue

**是什么**：尤雨溪 2014 年发布的渐进式框架。单文件组件（`.vue`：模板 + 逻辑 + 样式一体），响应式系统自动追踪依赖。

| | |
|---|---|
| **优势** | 上手最快；**官方全家桶**（路由 Vue Router、状态 Pinia 均官方维护，免选型）；**性能默认更好**（编译时优化 + 精确更新，无需手动 memo）；中文文档最佳 |
| **劣势** | 生态规模小于 React；大厂与外企机会较少；模板语法是额外 DSL；TS 支持历史上偏弱（Vue 3 已大幅改善） |
| **场景** | 中小型项目、快速交付、国内团队、后台管理系统 |
| **搭配** | Vite（同作者）+ Pinia + Vue Router + Element Plus |

### Angular

**是什么**：Google 出品的**完整框架**（不是库）。TypeScript 原生、依赖注入、RxJS、强约定。

| | |
|---|---|
| **优势** | **对 Java 开发者最亲切**（DI、装饰器、强约定，神似 Spring）；企业级完整方案；大团队一致性好 |
| **劣势** | 学习曲线最陡（RxJS 是道坎）；框架重、产物大；国内使用少、招聘少 |
| **场景** | 大型企业内部系统、团队有 Java/C# 背景、长生命周期项目 |
| **搭配** | 自带全套，无需选型 |

### Svelte / Solid

**是什么**：新一代**编译时框架**，**没有虚拟 DOM**——编译期直接生成精确更新 DOM 的代码。

| | |
|---|---|
| **优势** | 运行时体积极小；性能最优；代码量最少 |
| **劣势** | 生态小；招聘少；大型项目实践积累不足 |
| **场景** | 性能/体积敏感、嵌入式 Web、小型项目 |

### 选型速查

| 诉求 | 选择 |
|---|---|
| 生态与招聘优先 | React |
| 快速交付、少选型 | Vue |
| 最像 Spring、企业内部系统 | Angular |
| 极致性能与体积 | Svelte |

## ④ 构建工具层

### 为什么需要构建

浏览器不认识 TS、JSX、Vue SFC、Sass，也不认识 `import 图片`。此外还要打包（减少请求）、压缩、Tree-shaking（删除未用代码）、代码分割、加缓存哈希。

### Webpack

**是什么**：2012 年出现，统治前端近十年。

| | |
|---|---|
| **优势** | 功能最全；插件生态最大；极端定制能力强 |
| **劣势** | **慢**（大项目冷启动几十秒至数分钟）；配置复杂到成为一门手艺；内存占用高（大项目可达数 GB） |
| **场景** | 老项目维护、需要极端定制 |

### Vite

**是什么**：尤雨溪 2020 年发布。核心创新是**开发时不打包**——利用浏览器原生 ES Modules，改哪个文件只处理哪个文件，冷启动毫秒级、HMR 瞬时。生产构建用 Rollup（正转向 Rolldown）。

| | |
|---|---|
| **优势** | 极快；配置开箱即用；框架无关（React/Vue/Svelte 通吃）；已是事实标准 |
| **劣势** | 开发与生产曾用两套引擎（历史上有行为不一致的坑，正在收敛）；极端定制不如 Webpack |
| **场景** | **所有新项目的默认选择** |

### esbuild / swc

底层转译器，分别用 Go 和 Rust 编写，比 `tsc` 快 10–100 倍。**不做类型检查**（即上文「检查与转换分离」）。一般不直接使用，而是被 Vite、Next.js 内部集成。

### Turbopack / Rspack

Rust 编写的 Webpack 继任者。Turbopack 属 Next.js 官方；Rspack 由字节跳动开源，主打 Webpack 配置兼容。

### 两类性能，别混淆

- **构建工具的性能** = 开发体验：冷启动、HMR 延迟、构建内存占用
- **产物的性能** = 用户体验：包体积、代码分割、Tree-shaking 效果

前者影响你，后者影响用户。选型时分开评估。

## ⑤ 元框架层

### 要解决什么

纯 React（SPA）有三个先天缺陷：

1. **SEO 差**——首屏返回的是空 HTML，爬虫看不到内容
2. **首屏慢**——下载 JS → 执行 → 请求数据 → 渲染，瀑布式串行
3. **仍需另建后端**——React 只管 UI，API 要另起服务

元框架 = 框架之上的框架，把路由、渲染模式、数据获取、构建、甚至后端 API 整合进来。

### 渲染模式（核心概念）

| 模式 | 全称 | HTML 何时生成 | 适用 |
|---|---|---|---|
| **CSR** | 客户端渲染 | 浏览器里由 JS 生成 | 后台管理、登录后应用 |
| **SSR** | 服务端渲染 | 每次请求时在服务器生成 | 需 SEO 且内容常变（电商、资讯） |
| **SSG** | 静态生成 | 构建时一次性生成 | 文档、博客、营销页 |
| **ISR** | 增量静态再生 | 构建时生成 + 按需/定时更新 | 内容量大且更新不频繁 |
| **RSC** | React 服务端组件 | 组件在服务端执行，不下发其 JS | 减少包体积（React 新范式） |

**对 Java 开发者的类比**：SSR 本质上就是 **JSP / Thymeleaf / FreeMarker 的现代版**——服务端吐出完整 HTML。区别在于 SSR 之后会「注水」（hydration）：把 JS 挂上去，页面从静态 HTML 变成可交互的 SPA。所以它是"服务端模板渲染 + 单页应用"的合体，两头的好处都想要。

### Next.js

**是什么**：Vercel 出品，React 官方推荐的元框架。文件即路由、全渲染模式支持、内置 API Routes（可写后端）、图片与字体优化。

| | |
|---|---|
| **优势** | 渲染模式最全；生态最大；文件路由约定清晰；部署到 Vercel 一键完成；SEO 与首屏性能最佳解 |
| **劣势** | ① App Router（RSC）学习曲线陡，是范式级转变 ② 与 Vercel 绑定较深，自托管时部分能力打折 ③ 版本升级激进，破坏性变更频繁 ④ **多出一个 Node 服务要运维**（原本只需静态托管）⑤ 已有独立后端时，API Routes 属重复建设 |
| **场景** | 需要 SEO 的对外站点、内容站、电商；想用一套代码搞定前后端的小团队 |
| **不适合** | **纯后台管理系统**——登录后才可见，无 SEO 需求，SPA 完全够用，引入 SSR 只是徒增复杂度 |

### 其他

- **Nuxt**：Vue 生态的 Next.js，能力对位
- **Remix**：更贴近 Web 标准（表单、fetch），已并入 React Router v7
- **Astro**：内容站首选，默认零 JS，可混用多框架组件

### 选型判断

| 情况 | 结论 |
|---|---|
| 后台管理系统 | 不用元框架，Vite + React SPA 足够 |
| 对外网站需要 SEO | Next.js |
| **已有 Java/Go 后端** | 只取其渲染能力，**别用 API Routes**；或将其定位为 BFF 层 |
| 纯内容/文档站 | Astro 或 SSG |

## ⑥ 配套生态层

React 只管渲染，其余位置都要自己选。以下按职能列出，标注为什么需要它。

### 路由

SPA 里 URL 变化不能刷新页面，需要前端路由接管。

- **React Router**：最主流，v7 起融合 Remix 能力
- **TanStack Router**：类型安全更强，路由参数全程有类型

### 状态管理：先分清两种状态

**这是现代前端最重要的架构认知**：

| | 服务端状态 | 客户端状态 |
|---|---|---|
| 来自 | 后端 API | 纯前端 |
| 例子 | 用户列表、订单详情 | 主题、侧边栏开关、表单草稿 |
| 特点 | 异步、会过期、需缓存、可能并发重复请求 | 同步、即时、独占 |

**历史上最大的错误是用同一个工具管这两种状态**——Redux 时代把 API 数据也塞进 store，于是产生海量样板代码（action / reducer / saga 只为发一个请求）。

现在的答案是分开：

- **服务端状态 → TanStack Query**：自动缓存、去重、重试、失效重取、后台刷新、分页与乐观更新
- **客户端状态 → Zustand**（轻量首选）/ Jotai（原子化）/ Redux Toolkit（超大型、需要严格可追溯）

本质上，服务端状态管理就是**客户端的缓存一致性问题**——呼应 `competency-model.md` 里「前端是持有状态副本的客户端节点」。

### 数据请求

- **fetch**（浏览器原生，够用）/ **axios**（拦截器等便利功能，老牌）
- 关键不是选哪个，而是**外面包一层 TanStack Query**
- **类型链路**：`openapi-typescript` 可从后端 OpenAPI 文档生成 TS 类型——Spring Boot 配 springdoc 出文档，前端自动获得类型，端到端类型安全

### UI 组件库

| 库 | 特点 | 适用 |
|---|---|---|
| **Ant Design** | 组件最全，后台场景最强，国内主流 | 中后台管理系统 |
| **MUI** | Material Design，国际主流 | 对外产品 |
| **shadcn/ui** | 新范式：不是依赖，而是把源码复制进项目 | 需要深度定制 |
| **Radix / Headless UI** | 只提供行为与无障碍，不带样式 | 自建设计系统 |

### 样式方案

- **CSS Modules**：局部作用域，简单可靠
- **Tailwind CSS**：原子类，现事实标准；代价是 class 串很长
- **CSS-in-JS**（styled-components / emotion）：有运行时开销，且对 RSC 不友好，**正在退潮**
- 判断：新项目选 Tailwind 或 CSS Modules，避免运行时 CSS-in-JS

### 表单

**React Hook Form + zod**：非受控实现性能好，zod 同时提供运行时校验与类型推导——正好补上 TS「运行时零保护」的短板。

## ⑦ 工程化层

### 包管理器

| | 特点 |
|---|---|
| **npm** | Node 自带，无需安装 |
| **yarn** | 早期改良者，现已被追平 |
| **pnpm** | **推荐**：硬链接共享依赖省磁盘、安装快、严格依赖树（杜绝幽灵依赖） |

### 代码规范

- **ESLint**（查问题）+ **Prettier**（统一格式）——当前主流组合
- **Biome / oxlint**：Rust 编写，快 10–100 倍，lint 与 format 一体，新兴趋势

### 测试

| 工具 | 层次 |
|---|---|
| **Vitest** | 单元测试，Vite 生态原生，替代 Jest |
| **Testing Library** | 组件测试，**测行为不测实现** |
| **Playwright** | E2E，微软出品，当前最强 |

**与后端的投入产出差异**：UI 变化频繁，快照测试极易碎，覆盖率数字意义有限。重点应放在**纯逻辑单元测试**与**关键路径 E2E**，而非全面组件测试。

### 类型检查

`tsc --noEmit` 单独在 CI 执行——因为 Vite 与 Node 运行时都**不检查类型**。

### 部署

- 纯静态（SPA/SSG）：Nginx / CDN / 对象存储，成本极低
- SSR：需要长驻 Node 进程，Docker 或平台托管
- 缓存策略：入口 HTML 不缓存，带哈希的静态资源永久缓存

### 监控与可观测性

**前端的可观测性是另一套体系**——错误发生在用户设备上，不主动上报就完全不可见，后端的日志与 APM 在此无效。

- **Sentry**：前端错误监控与 source map 还原
- **Web Vitals**：LCP（加载）、INP（交互响应）、CLS（布局偏移）——Google 定义的用户体验核心指标
